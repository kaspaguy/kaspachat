# Kaspaveil Protocol — Specification v0.3 (draft)

**Status:** Phase 1 draft, 2026-09-29. v0.2 added the free/paid tiers; v0.3 adds the black-box treasury, the hard-coded 25/75 split, the reserved-name list and the bouncer role (Kaspaguy, same day). 2026-09-30: the treasury became a throttled spending pot with no monthly signing (§8.3, SC-0012). Kaspaveil is the protocol, KaspaChat the app, Kaspaguy the studio (final, Kaspaguy 2026-09-29). Nothing deployed (testnet-10 checks only: lane transport and the treasury hot wallet, §10). Items marked **[DECIDE]** need an owner decision; **[PROTO]** is proven by a local prototype; **[TODO]** is still unspecified.

Kaspaveil is an end-to-end encrypted, metadata-private messaging protocol on Kaspa L1 (post-Toccata). This document is the protocol, not the app: any client that follows it can interoperate.

---

## 1. Goals and threat model

**Principle:** metadata privacy is part of the protocol, not a feature to add later. No version of Kaspaveil may ship that leaks who talks to whom with a plan to fix it afterwards (the Nostr NIP-04 → NIP-17 lesson).

**Protects:**
- **Content.** Only the participants can read a message. The Kaspaveil operator has no keys and can't read anything.
- **Authenticity.** The recipient knows the message came from the holder of the sender's registered key and wasn't altered.
- **Social graph.** An observer of the chain can't tell who is talking to whom: recipients are never on-chain, and senders aren't either when sending through the relay (the default).
- **Past and future messages.** Stealing a device key doesn't expose earlier messages (forward secrecy), and the conversation heals itself afterwards (post-compromise security).
- **"Harvest now, decrypt later."** All ciphertext is public and permanent, so key exchange is hybrid post-quantum from day one.
- **Key substitution.** A lying server can't swap someone's key, because name→key bindings are committed on-chain (§3).

**Doesn't protect (stated openly):**
- **Sender linkability when the relay is bypassed.** Everyone normally sends through the Kaspaguy relay with blind tokens, which hides the sender on-chain (§8). A user who sends from their own wallet instead (for example when the relay is down) exposes that wallet's address, so those messages can be linked to each other (not to their recipients).
- **The relay operator** never sees content or recipient, and blind tokens stop it linking a message to the account that paid. **But it does see which IP address submitted which message, and when**, and can match that to the message appearing on-chain. Mitigations: the desktop and phone apps submit over Tor by default (built 2026-10-22; iPhone written 2026-10-23, untested); the relay holds each message for a random 0.5–4 s and broadcasts it with up to 4 others picked at random from those waiting, in random order, so on-chain order and timing don't mirror submissions (built 2026-10-22, `tools/chaind`); cover traffic mixes in dummy submissions. The web app on clearnet gets the mixing only.
- **Timing.** A message appears on-chain when it's sent. Correlating it with online activity is possible for a global observer.
- **Network metadata.** The indexer sees client IP addresses and which tag buckets they fetch (mitigations in §6.3).
- **First-contact counts per inbox bucket.** Anyone who knows a user's public identity key can compute their inbox bucket (§6.1) and count the first contacts landing there, and when. There are 4,096 buckets shared by all users, so at scale this is a count for a crowd, not a person; **early on, with few users, a bucket may hold just one person**, so a watcher could learn that *someone* contacted them. Mitigation: cover traffic also sends dummy first contacts into random inbox buckets.
- **Endpoint compromise.** Malware on a device reads what the user reads.
- **Web delivery.** A web app is served fresh on every visit, so the server operator could serve malicious code. Mitigated by reproducible, signed builds; eliminated by the native apps.

**Consequence 1 — cost (measured on testnet-10, 2026-09-29).** The minimum fee must cover the larger of compute mass and *normalized transient mass* (transaction byte size × 4, weighted × 0.5 against the block limits), at 100 sompi per gram. For a 2 KB message the size term binds: compute 3,674, transient 9,256 → normalized 4,628 → **minimum fee 462,800 sompi = 0.004628 KAS** for a message paid from the sender's own wallet. The node rejected 0.00460 KAS ("under the required amount of 462800 for normalized transient mass 4628") and accepted 0.00465 KAS. A relay-paid message also carries the treasury script and root certificate (2,635 bytes in all), and it measured at **527,000 sompi = 0.00527 KAS** on testnet-10: normalized transient mass 5,270 binds (compute 5,105, including a compute budget of 21 units for 201,250 script units). The node rejected 0.00500 KAS ("under the required amount of 527000"). **Since SC-0012 (2026-09-30)** a relay-paid message is paid by the throttled spending pot (§8.3), whose larger script makes it 3,104 bytes: **620,800 sompi = 0.006208 KAS**, measured on testnet-10 (normalized transient mass 6,208 binds; compute 4,574 with a compute budget of 11 units; the node rejected 620,799). **Since SC-0013/SC-0014 (2026-10-11)** every payload is 1,536 bytes, so a relay-paid message is 2,597 bytes: **519,400 sompi = 0.005194 KAS**, measured on testnet-10 on 2026-10-11 (normalized transient mass 5,194 binds; compute 4,067; the node rejected 519,399 as non-standard). **Under load, the minimum isn't enough to be mined promptly:** on 2026-10-11 testnet traffic paid 115–190 sompi/gram (node fee estimate) and chained messages at the floor stayed unconfirmed for over a minute, so the relay must price from the node's fee estimate, not the floor (the pot allows up to 1 KAS a message). At KAS ≈ US$0.04 that is about 0.021 US cents per message.

**Consequence 2 — storage.** Nodes forget message data after about 30 hours; the relay/indexer keeps it for 7 days (§8.1), and each client deletes its copy 30 hours after it arrives (unless every member is Plus and has opted out). **The indexer is a required component** (§6); without an archive, anything older than 30 hours is unrecoverable from the network.

## 3. Identity and usernames

### 3.1 Keys (per identity)
- **Owner key:** secp256k1 Schnorr (x-only, 32 bytes). Controls the registry entry; covenants can check it (`checkMsgSig`).
- **Identity DH key:** X25519.
- **Signed prekey:** X25519 plus ML-KEM-768 (FIPS 203), rotated about every 7 days, and never more often (`WIRE_FORMAT.md` §4.2). There is no separate identity KEM key (as in Signal's PQXDH); see `WIRE_FORMAT.md` §2.
- All keys are derived from one 24-word recovery phrase with domain-separated HKDF. **No recovery exists without the phrase.**

### 3.2 Key bundle
`Bundle = {version, ownerPub, idX25519, spkId, spkX25519, spkMLKEM, created, devices[]}`, signed by the owner key (1,358 bytes, fits one payload; exact layout in `WIRE_FORMAT.md` §3). **[PROTO]**

It's published as a transaction on the Kaspaveil lane (§5) and archived by indexers. **Clients accept a bundle only if its signature verifies against the owner key that the registry maps the name to.** Rotating the bundle needs no registry update.

### 3.3 Registry (covenant) — **[PROTO]**
- Stored as an **indexed Merkle tree**: leaves form a sorted linked list of 56-bit name keys (`key = first 7 bytes of BLAKE2b(name)`).
  - Leaf = `BLAKE2b(key‖nextKey‖nextIdx‖owner‖expiry‖nonce)`, depth 20 per shard, so about 1M names per shard. The nonce makes every owner signature single-use.
  - Shard state also holds the registrar and price keys, the monthly price, their nonces, and the public prepaid counters. Every signed message is domain-separated by registry ID and shard ID.
- **Sharded:** 16 shard UTXOs, one per top 4 bits of the key (`shard = key >> 52`), each with its own covenant ID. Shards update in parallel. Clients compute the shard from the name; each shard's covenant carries a constant `shardId` and requires `key >> 52 == shardId`. **[PROTO]**
- **Registration:**
  - Proves the "low leaf" that brackets the new key, which proves the name is free.
  - Relinks it and appends the new leaf.
  - Checks the name charset `[a-z0-9-]` and length 3–20, with no leading or trailing hyphen.
  - **Every registration needs the bouncer (decided, Kaspaguy 2026-09-29):** the free path (`registerDefault`), the direct path (`registerDirect`) and the credit path (`registerPrepaid`) all require the registrar's signature over **the name and the owner key together**, domain-separated per path. **[PROTO]**
  - **Direct path:** additionally requires output 1 to pay Kaspaguy 25% and output 2 to pay the treasury reservoir 75% of `months × monthly price`, and stores the expiry. A one-month payment must go to the one-month reservoir and a 2–12 month prepayment to the prepayment reservoir (SC-0015). **[PROTO]**
  - **Credit path:** no payment outputs (paid earlier through the payment covenant); increments the public prepaid counters (§8.5a). **[PROTO]**
  - Carries the state forward with `validateOutputState`, and the registry UTXO's value may not be drained. Every entry also requires that exactly one input and one output carry the shard's covenant ID, at output 0, so no spend can end or fork the canonical lineage (SC-0016).
- **Prototype (v2):** `contracts/registry_shard.sil`, compiled script about 51 KB, entries `registerDefault`, `registerDirect`, `registerPrepaid`, `renewDirect`, `renewPrepaid`, `transfer`, `sell`, `reclaim`, `release`, `settleAuction`, `settleAuctionPrepaid`, `claimReleasedDirect`, `claimReleasedPrepaid`, `setPrice`, `rotateKeys`.
  - Local test suite (real rusty-kaspa script engine via the Silverscript debugger, real BIP-340 signatures, each shard UTXO given a realistic creation time): **75/75 pass**. Valid cases for every entry (including free names at re-roll 0 and 2; reclaim exactly at the end of grace; an auction win, including by a rotated-in auction key on a name held before the rotation; release exactly 6 months into a hold; re-registering a released name directly or with credits; an auction winner's renewal from day 31 and lapse back to auction), and rejections for: reclaim one block early, reclaiming a free name or a name already held; renewing a held name; an auction settlement short-changing the treasury, not signed by the auction key, below the reserve, or on a name nobody reclaimed; transferring a held name; release one block early or of a name that isn't held; claiming a released name without the doorman or while it is still held; a free name without the bouncer, someone else's derived free name, a hand-picked `kv` name, a third re-roll; a direct registration without the bouncer's signature (the reserved-list bypass); either share 1 sompi short; the wrong shard; draining the registry's own value; a prepaid registration signed by a non-registrar, hidden from the public counters, or stretched from 2 to 12 months; an underpaid renewal; a prepaid renewal signed by a non-registrar; a transfer signed by someone else; **replaying an old transfer signature**; a sale with Kaspaguy's 15% or the seller's 92.5% one sompi short, the payout redirected, a lower price than the seller signed, or no owner signature; price changes of ±51%, below 10 KAS, above 1,000 KAS, by the wrong key, or replaying a used signature; key rotation signed by the registrar instead of the root; and a rotation that also sneaks in a price change.
  - **Time cut-offs (tested 2026-09-29, debugger patched to set UTXO creation times — `contracts/tools/debugger_utxo_daa.patch`):** a renewal passes when the shard's UTXO was created on the last block of grace and fails one block later (direct and prepaid); a sale passes on the name's last block and fails one block after expiry.
  - **Renewal and sale cut-offs are soft.** Kaspa can prove a deadline has passed, but it cannot prove it hasn't: a covenant can check only two times, the transaction's lock time (`tx.daa`, which the network accepts only once that DAA score has passed, so it is a lower bound on now) and the DAA score at which each input was created, and neither is the current time. So "is this before the deadline?" is checked against the DAA score at which the shard's on-chain record was last updated, not against the true current time. If nobody has touched the shard since a name's expiry or grace period ended, a late renewal or sale still goes through — the contract has no way to tell that the deadline has already passed (tested: *renewDirect after grace on a shard untouched since before grace ended* passes). The gap closes the moment anyone touches the shard: a `reclaim` makes the name impossible to renew, and `reclaim` is permissionless, so anyone can close it. In practice, the doorman calls `reclaim` when each name's grace ends (§8.5), which makes the cut-off exact for every name that lapses and sends it to auction on time. Until that reclaim lands, the app warns a buyer that a name is past its expiry, and the buyer should know the sale may not be deliverable if a reclaim lands first (the sale is one atomic transaction, so it then simply fails and no payment moves). With the doorman's reclaim in place, the residual window is short (minutes, not indefinite), and the harm is bounded: a late buyer still has to renew within the grace period to keep the name.
  - **Soft deadline cut-offs — decided (Kaspaguy, 2026-09-29):** the doorman reclaims at each name's grace end (making the cut-off exact in practice), and the app warns buyers about names past expiry; the residual window is short and the harm bounded. No periodic shard touches (no standing expense).
  - Cost: about 80 BLAKE2b calls per registration, roughly 1 compute-budget unit. Every registry transaction carries the whole 51 KB script (P2SH), so each registry action costs roughly 0.05–0.1 KAS in network fees; well within the per-block mass limits.
  - **Signature-check budget:** Kaspa's relay refuses a script-locked input whose script contains more than **15** signature checks. The registry has **12**, so at most 3 more signed actions fit; beyond that the registry must be split into separate covenant templates.
- **Lookups are trustless.** A client fetches the shard UTXO state from any Kaspa node and a Merkle proof from any indexer, so an indexer can't lie about who owns a name. That gives built-in key transparency.
- **No admin key.** Nobody, including the operator, can seize, delete or censor a name. Upgrades happen by migrating to a new registry version that imports the old root.
- **Migration path.** Clients pin a list of accepted registry lineages, not a single one. A new version is added in a client release, and it starts from the old root (committed in its genesis state), so every existing name carries over. Old versions are frozen read-only once their successor is live; clients resolve a name from the newest version that contains it.
- **Canonical registry** = the covenant ID lineage from the genesis transaction, which is pinned in the clients. Clones can't fake it.

### 3.4 Default (free) and Plus (paid) names
- **Default (free tier):** assigned, never chosen. `name = "kv" ‖ base32(BLAKE2b(ownerPub ‖ n))[0..8]` (alphabet `a–z2–7`, first 40 bits of the hash, big-endian) with n ∈ {0, 1, 2} as one byte (vector `registry-default-names`), which gives the "couple of free changes". The covenant checks the derivation, so free defaults can't be squatted; the bouncer co-signs after its per-device checks. Expiry 0 means free and permanent, so free names can't be renewed or sold. **[PROTO]**
- **Plus names (paid tier):** chosen (e.g. `@catch22`, `@dog-cat-21`), held while the subscription is paid, resaleable. Format, price and split are in §8.2.
- **Switching names (SC-0022):** when someone starts going by another of their names, their app tells each established contact once (`WIRE_FORMAT.md` §7.3). The contact checks the name against the registry before showing it, and reads the tier from it, so a switch to a Plus name gives the right timer and name everywhere. It costs one message per contact.
- **Reserved list:** enforced by the bouncer at registration (§8.4). It covers impersonation targets (`kaspa`, `admin`, `support`, exchange and brand names) because **with no admin key there are no takedowns later**.
- **Visible tier, stated openly:** the directory shows whether a name is a free default (`@kv…`, no expiry) or a Plus name (chosen, with an expiry). Messages never carry names, so this reveals nothing about who talks to whom; it only shows that a name belongs to a subscriber.
- **Front-running — decided: no commit→reveal (Kaspaguy, 2026-09-29).** Every registration carries the bouncer's signature over the name and the owner key together, so a bot copying a pending registration from the mempool can't change the owner; the copy would only register the name to the original owner. The bouncer is the arbiter of who gets a name (§8.5). Registration stays a single step.
- **Transfers** are authorised by the current owner's signature over `(name, newOwner, nonce)`, so a mempool copier can't redirect them. A sale runs atomically in one transaction (buyer pays seller, name moves to buyer, 7.5% + 7.5% to Kaspaguy) through the covenant.

## 4. Encryption

- **Session setup: PQXDH-style.**
  - X25519 DH over identity, signed-prekey and ephemeral keys, plus ML-KEM-768 encapsulation to the recipient's prekey.
  - The secrets are combined with HKDF-SHA-256.
- **Ongoing: double ratchet** (X25519 DH ratchet plus symmetric chains).
  - A post-quantum KEM ratchet step (ML-KEM-768) runs at least every 50 messages or every 24 hours, whichever comes first. This is in the spirit of Signal's 2025 SPQR "triple ratchet". **[PROTO]** An offer/answer pair of ordinary messages (kind 0x05); the shared secret enters the root key at one step both sides can identify, and it also re-keys both tag chains, so after a device compromise the conversation's tags become unlinkable again, not just its content (`WIRE_FORMAT.md` §4.5). Tested against an attacker who has broken X25519 but not ML-KEM: she loses the conversation, both directions, one round trip after the step. A KEM step protects messages from the first re-keyed chain onward; messages already in flight are covered by the next step. Tags also re-key at each step, so tag recognition heals at the same interval as message keys.
  - Old keys are deleted immediately, except skipped message keys (for messages that haven't arrived yet), which are kept for at most 7 days (`WIRE_FORMAT.md` §4.1).
- **Message encryption:** XChaCha20-Poly1305. The header is encrypted too.
- **Authenticity — decided: deniable by default** (the Signal model: the recipient knows who sent a message but can't prove it to anyone else), with an **optional per-message "signed" flag** that adds an owner-key signature inside the ciphertext for cases where proof matters. **[TODO]** Not in the v1 wire format yet: the header `flags` byte is reserved (senders write 0, receivers ignore it) until this is specified.
- **Groups — decided cap: 4 members.**
  - **Pairwise fan-out (built 2026-09-29):** a group message is sent over each other member's own pairwise ratchet, one payload per recipient. (The earlier draft said "encrypt the body once and wrap its key per member"; with one fixed-size payload per transaction, each wrapped key would need its own payload anyway, so that costs N+1 transactions instead of N and adds nothing.) **[PROTO]**
  - There is no shared group key, so **membership changes need no re-keying**: a removed member simply stops receiving copies, and a new member starts. Forward secrecy, healing and the KEM step all come from the pairwise ratchets. To an observer a group message is just N ordinary payloads.
  - Membership is a **group-state message** (kind 0x03: group ID, epoch, admin, up to 4 members with their keys and names), signed by the admin's owner key inside the ciphertext. Only the admin can change it, epochs only move forward, and a state that doesn't list you can't add you to anything. Every group text (kind 0x04) carries its epoch and a message ID shared by all copies. A text from an older epoch that arrives after a change is shown with a notice; nothing is produced for a removed member; a member added later never receives earlier epochs. A text whose state hasn't arrived yet is held and retried (different pairwise sessions don't keep order between them).
  - Members who have never talked reach each other by first contact (first contacts may carry kinds 0x01, 0x03, 0x04). Since SC-0013 a first contact holds at most 242 bytes of content, so a group text of up to 205 bytes travels inside it, but a group state (288 bytes for 2 members, 458 for 4) never fits: the sender then sends a first contact with an empty text, which only opens the session, and the group message right after it on the new session (`WIRE_FORMAT.md` §4.6). Reaching a stranger with a group state therefore costs 2 payloads instead of 1.
  - **Cost:** one relay fee per recipient, so a message to a full group of 4 costs 3 × 0.005194 KAS: 3 individual messages per send (2 in a 3-person group). The published line says so (§8.2, decided by Kaspaguy 2026-09-29).
  - Larger groups need sender keys or MLS (RFC 9420): a v2 topic.
- **Libraries:** audited, standard ones only (`@noble/curves`, `@noble/post-quantum`, `@noble/ciphers`, `@noble/hashes`). No home-made primitives. Test vectors are published.

## 5. On-chain message format

- **Lane:** Kaspaveil namespace `subnetwork_id = "KVL" 0x01 ‖ 0x00×16` (bytes 1–3 non-zero, as the lane rules require). Indexers subscribe to one lane only; KIP-21 commitments make "you received every message in the lane" provable later.
- **Exact byte layouts, KDF labels and test vectors: `WIRE_FORMAT.md` and `protocol/vectors/v1.json`.** **[PROTO]** Reference implementation in `protocol/src/`, 77/77 tests:
  1. the recovery phrase derives the same keys every time, and distinct prekeys per index;
  2. bundles verify only against the registry's owner key, reject tampering, and fit one payload;
  3. first contact then a two-way conversation, every payload exactly 1,536 bytes, first contact landing in the inbox bucket;
  4. out-of-order and lost messages still decrypt, and replays are rejected (a late message from the peer's older ratchet key: vector `ratchet-late-from-older-ratchet-key`);
  5. rejection of a first contact not addressed to you, a tampered first contact, someone else claiming a registered name, and a tampered message (the session survives the failed attempt);
  6. no tag or 32-byte cleartext field repeats across a 21-message conversation;
  7. size limits (242-byte first-contact text, 1,404-byte text), cover traffic and bucket helpers;
  8. the implementation reproduces the published vectors byte for byte (including a full KEM step and a group state + text);
  9. conversation settings (3 tests: the timer and screenshot-protection rules, and the kind 0x06 round trip);
  10. the KEM ratchet step (7 tests: full step, healing against an attacker who has broken X25519, crossing offers, lost answer and re-offer, late messages across the tag switch, stale steps, the 50-message / 24-hour policy);
  11. groups (4 tests: four strangers reaching each other by first contact, removal and re-adding without re-keying, forged/forwarded/replayed states and non-member texts, sizes).
- **One fixed payload size: 1,536 bytes** (SC-0013; 2,048 before 2026-10-11) for every message type (first contact, text, group, ratchet step, bundle, cover traffic), so size reveals nothing.
- **Payload layout:**
  - `ver(1) ‖ tag(16) ‖ field(32) ‖ …` (exact layouts per type in `WIRE_FORMAT.md` §4: the 32-byte field is the ephemeral key in a first contact, 32 random bytes in an ongoing message)
  - **`ephemeral` is a one-time key only in first-contact messages; in every other message it's 32 fresh random bytes.** The ratchet's public key travels inside the encrypted header, so no value repeats across a conversation's messages. Nothing constant ever appears in the clear in a message; the one deliberate exception is a bundle publication (`WIRE_FORMAT.md` §4.3), which is public directory data and recognisable by design.
  - `tag` is the only routing field (§6).
  - The first-contact ciphertext carries the PQXDH initial message; others carry a ratchet message.
- **Transaction:** a v1 Kaspa transaction on the Kaspaveil lane with the 1,536-byte payload in its payload field, one payload per transaction; sent by the relay from the treasury's spending pot (default) or from the sender's own wallet (fallback). Exact rules: `WIRE_FORMAT.md` §5. No output reveals the recipient. Text limit: 1,404 bytes per message (242 in a first contact); longer texts span several messages.
- **Attachments [v2]:** encrypted blobs off-chain (indexer or IPFS), with the key and hash inside a message.

## 6. Routing, indexer and privacy of retrieval

### 6.1 Tags
- **First contact:** `tag = BLAKE2b-128("kasveil/v1/fc-tag" ‖ ECDH(ephemeral, recipient idX25519))` (16-byte output length, not a truncation; `WIRE_FORMAT.md` §1), with its first 12 bits set to the recipient's **inbox bucket** (derived from their identity key), so recipients only scan their own bucket. Routing is classical X25519; sender identity and content are post-quantum protected (`WIRE_FORMAT.md` §4.2). The inbox bucket is computable by anyone who knows the recipient's identity key, so first-contact *counts* per bucket are watchable (§1).
- **Ongoing conversation:** each direction has its own tag key (`KDF(SK, "tag-i2r")` / `KDF(SK, "tag-r2i")` from the first contact, re-keyed at every KEM step) and `tag_n = BLAKE2b-128(tagKey ‖ u32(n))` (`WIRE_FORMAT.md` §4.1, §4.5). Recipients know exactly which next tags to watch for. Tags never repeat, so they can't be linked to each other.

### 6.2 Indexer (anyone can run one)
- Follows the Kaspaveil lane through a rusty-kaspa node, archives beyond the 30-hour pruning window, and serves messages by tag prefix.
- Also rebuilds registry state and serves Merkle proofs, and serves the latest bundles.
- Holds only public data (ciphertext and public keys). Several independent indexers is the goal. Clients can point at their own.
- **The indexer must run its own Kaspa node; public explorers are not reliable enough to serve as a data source** (confirmed on testnet 2026-09-29: the public TN10 explorer's transaction index was so far behind it didn't list even a normal faucet payment).

### 6.3 Retrieval privacy
- **Registry lookups use buckets too:** to look up `@bob`, a client fetches every registry entry whose name key shares a short prefix (for example 8 bits, ~1/256 of all names), then picks Bob's entry locally and checks its Merkle proof against the on-chain root. The indexer learns a bucket, never the name being searched for.
- Clients fetch by a **tag bucket**, receive every message in that bucket, and filter locally. The indexer learns a bucket, not a conversation. **Pinned:** `bucket = (tag[0] << 4) | (tag[1] >> 4)`, the first 12 bits of the tag, big-endian (4,096 buckets). The other 116 bits are ignored for bucketing and used only by the client to match. Registry buckets are pinned the same way: `bucket = BLAKE2b(name)[0]` (256 buckets). Every indexer must use exactly these, so clients and indexers interoperate.
- **Correlation, stated plainly:** without Tor, a single indexer *can* link one client's bucket requests over time by IP address and build a profile of its buckets. It still can't read anything or tell which messages in a bucket are the client's.
- **No IP logs (Kaspaguy, 2026-10-10).** Kaspaguy's relay, indexer and doorman keep no IP logs: no access logs with addresses, nothing per IP on disk. Anti-abuse rate limits use counters in memory only, short-lived (minutes) and never written out. The relay's 7-day store is ciphertext kept for offline delivery, not a record of who submitted it. Clients can't verify an operator's logging, which is why Tor stays the default in the native apps.
- **Tor by default where possible (built 2026-10-22 for desktop and Android; iPhone written 2026-10-23, not yet tested on a device).** The apps embed Tor (Arti, `tor/`) and reach the relay and indexer at their .onion address by default. If Tor can't connect, the app says so and keeps trying; connecting directly is the user's switch (Account → Connection), never an automatic fallback. iPhone: the same library as a static iOS framework (`tools/build-apple.sh`). iPhone push (opt-in) is the exception: the notification extension runs in its own process and fetches new messages directly. A normal browser can't route a web page's requests through Tor, so the web app offers a .onion mirror for Tor Browser users and says so clearly. That's one more reason the native apps are the long-term clients.
- Private information retrieval (PIR) is a later research item.
- **Cover traffic — decided: on by default,** with a visible toggle and a daily budget (a fraction of a KAS a day). Clients send dummy messages indistinguishable from real ones. Default-on matters: if only a few users opt in, opting in is itself a signal.

## 7. Devices
- **Notifications without push (Kaspaguy, 2026-10-16).** No Apple or Google push service: they would learn when a device gets a message. The apps show their own local notifications while they run, saying "New message" (or "New message request") without the sender's name unless the user turns names on. At sign-up the app asks for notification permission and, on Android, for background use: a battery-optimisation exemption plus a quiet foreground service ("KaspaChat is connected") keep the app checking for messages when it's in the background. Desktop apps keep running when minimised. iOS suspends apps shortly after they leave the screen, so without push an iPhone gets its messages when the app is opened; the app says so at sign-up.
- **iPhone push, opt-in and off by default (Kaspaguy, 2026-10-16).** Account → Notifications → "Wake for new messages while KaspaChat is closed". The app registers its Apple device token with Kaspaguy's push service (`relay/src/push.ts`) together with the buckets of its upcoming message tags (at most 64; never the fixed first-contact inbox bucket, which would identify the phone for good). When a message lands in one of those buckets, the service asks Apple to wake the phone. The phone's Notification Service Extension fetches the new messages in those buckets, compares their tags with the tags the app expects (kept in the app group, never sent anywhere), and shows "New message" only on a match; otherwise it shows nothing, using Apple's notification-filtering entitlement for end-to-end encrypted messengers. Cover traffic and other people's messages share buckets, so some wake-ups are for nothing. Message requests from new people still wait until the app is opened.
  - **Stated plainly, and shown in the app next to the switch:** Apple and the push service see when a phone is woken, never who wrote or what. With it on, it may be possible to link two people who message each other from the timing of their wake-ups. The service keeps device tokens and bucket numbers only, deletes a registration 3 days after the app last refreshed it, and logs no IP addresses.
  - Android and desktop don't use push: they run in the background (above).
- **Block and report (2026-10-16; Apple guideline 1.2, Google Play user-generated content policy).** Blocking is local: messages and notices from a blocked owner key are dropped, a first contact from them opens nothing, and in a group they stay a member (only the admin changes members) but their messages are hidden. They aren't told. A report sends Kaspaguy only what the reporter chooses (the reported name, a reason, a note, optionally the last 20 messages between them in that chat); the reporter's name isn't sent. The relay stores reports without any IP address; `relay/scripts/reports.ts` lists and closes them. Closing a report deletes its message text and note; every report is deleted 90 days after it arrived.
- The v1 web app is single-device. The **protocol reserves `devices[]`** in the bundle: each device has its own keys, signed by the owner key, and messages fan out per device.
- The desktop QR link (Phase 5): the phone shows a QR code with a one-time key, the desktop and phone set up an E2E channel, and the phone signs the new device into the bundle.

## 8. Tiers and economics (v0.3)

### 8.1 Free tier
- **Name:** the code-style default only (`@kv7f3q9x`), free, with up to 2 re-rolls (§3.4).
- **Messages auto-delete after 30 hours.** The app deletes the message *and the keys that decrypt it* 30 hours after it arrives. The ciphertext stays on-chain or in archives, but **once a device has purged those keys, even a later compromise of that device can't decrypt it**. This is forward secrecy by deletion: it can't stop the other person copying or photographing a message before then, and it depends on the app doing the deletion. The deletion and the timer rule are in the open protocol library (`protocol/src/retention.ts`, `settings.ts`), and the apps call them, so anyone can check the 30 hours.
- **Both sides delete.** The disappearing timer belongs to the **conversation** and every participant's app honours it, sender included (the sender's app deletes its sent copy and keys on the same clock). Free users always have it on at 30 hours. **Decided (Kaspaguy, 2026-09-29):** a Plus user can turn the timer off, and keep history in their archive, only in conversations where every member is Plus. The app checks every member's tier (visible in the directory, §3.4) before offering the toggle. **The timer is on unless every current member is Plus and every Plus member has chosen to turn it off;** adding a free member, or a Plus member's subscription lapsing, turns it back on for the conversation at 30 hours. **Decided (Kaspaguy):** when it turns back on, it applies to messages from that moment. History kept while every member had opted out **stays with the members who kept it, and a newly added member never receives it**: a new member's pairwise sessions start at the moment they join, the protocol has no way to forward earlier messages, and the apps offer no "share history" option.
  - *All-Plus, timer off:* everyone's app keeps everything; everyone opted in.
  - *All-Plus, timer on* / *any free member:* everyone's app, sender included, deletes after 30 hours; the toggle isn't offered when a free member is present, so a Plus member's archive can never silently out-retain a free member.
  - *Stated plainly:* any participant can still copy, screenshot or photograph a message before it's deleted. The timer stops apps keeping messages; it can't stop a person.
  - **Grace period counts as Plus — decided (Kaspaguy, 2026-09-30).** A name in its 30-day grace period counts as Plus for the timer rule and for switching screenshot protection on. Someone renewing late should not have their timer flip mid-grace. The check uses the DAA score of the latest block the app knows about, against the expiry the registry stores in DAA score (the same clock the covenant uses for expiry); so a name counts as Plus until expiry + 30 days has passed at that score, whether or not a `reclaim` has landed yet. (Two apps a few blocks apart can disagree for those seconds at the exact boundary.)
- **Delivery window — decided: 7 days.** Relay servers keep the lane's ciphertext for 7 days, so a user who's offline still receives messages when they come back; each message is then deleted 30 hours after it arrives. The indexer can't tell free from paid messages (they're identical), so this window applies to all ciphertext.
- **Sending — decided: top up, then send through the relay.** A free user tops up with KAS; the payment is split 25% Kaspaguy / 75% treasury exactly like Plus (the same hard-coded covenant), and they receive message credits (blind tokens) at the same rate as Plus: about **1,400 messages per 10 KAS at today's fees** (7.5 KAS treasury share ÷ 0.005194 KAS per relay-paid message since SC-0013; ~1,200 at 0.006208 KAS), so the 20 KAS minimum top-up buys about 2,900. So free users also send without their address showing on-chain.
  - **Welcome credits:** every new free name gets **10 free messages** (Kaspaguy: 5–15), paid by the treasury. Anti-abuse: the bouncer rate-limits new free names (per device and per IP, plus a small proof-of-work), so farming free names for their welcome messages costs more than it's worth.
  - **Low-balance notices inside the chat:** the app counts its own credits (it holds the tokens, so no server needs to know) and posts a notice in the conversation list when about 20% of the last top-up is left, again at 10 messages, and at zero, with a one-tap top-up.
  - **Minimum top-up — decided: 20 KAS** (≈ ฿30), which splits cleanly into 5 KAS Kaspaguy / 15 KAS treasury. Enforced by the payment covenant.
  - **Anti-abuse, machine level:** one free name per device where the platform can prove it, without Kaspaguy learning who the device is:
    - **Android:** Play Integrity plus *device recall* (Google stores 3 bits per device that survive reinstalls and factory resets: "this device already took a free name").
    - **iPhone / Mac:** App Attest in the app, and Private Access Tokens in Safari (Apple vouches the device is real and rate-limited, without identifying it).
    - **Other browsers and Tor:** a proof-of-work puzzle (about 30–60 seconds of computing per free name) plus per-IP limits.
    - Attestation goes through Google/Apple, so it's used **only** at free-name creation, never for messaging.
    - Welcome messages to strangers land as **message requests** the recipient must accept, so farmed names can't spam silently.
### 8.2 Plus (paid tier)
- **Name:** a chosen name, e.g. `@catch22`, `@dog-cat-21`, `@fat-32`.
  - Charset `[a-z0-9-]`, 3–20 characters, no leading or trailing hyphen (underscore dropped to cut look-alikes). **[PROTO]**
  - **Reserved names aren't sold on sign-up** (§8.4): short names, dictionary words, first names, places and numbers are held for auction or later release; brands, projects, officials and public figures are protected; offensive names are blocked.
- **Price:** about **100 KAS per month** (≈ US$4.50 / ฿151 at 2026-09-29 prices), 1–12 months per payment. **Decided: price key with hard limits.** The monthly price lives in the registry's state; a Kaspaguy price key can update it and nothing else, only within **10–1,000 KAS per month** and by at most **±50% per change**. This lets Kaspaguy hold a roughly steady Baht price as KAS moves. A stolen price key can only set a silly price within those limits until it's rotated (§8.5); no funds are at risk. **[PROTO]**
- **Payment split, hard-coded in the registry covenant: 25% → Kaspaguy dev wallet, 75% → the treasury.** The percentages are constants in the contract code (`DEV_PCT = 25`, `TREASURY_PCT = 75`). A deployed covenant can't be edited by anyone, and clients accept only registry versions carrying this split. **[PROTO]**: 13/13 tests, including 1-sompi underpayments of either share, the treasury share sent elsewhere, and everything paid to dev.
- **Name lifetime:** the registry leaf stores an expiry (`now + months × 30 days` in DAA score); renewal extends it from the current expiry. **[PROTO]** **Grace period — decided: 30 days** after expiry. **Decided (Kaspaguy, 2026-09-30):** A name in its 30-day grace period counts as Plus for the timer rule and for switching screenshot protection on. Someone renewing late should not have their timer flip mid-grace. The check uses the DAA score of the latest block the app knows about, against the expiry the registry stores in DAA score (the same clock the covenant uses for expiry); so a name counts as Plus until expiry + 30 days has passed at that score, whether or not a `reclaim` has landed yet. (Two apps a few blocks apart can disagree for those seconds at the exact boundary.)
- **Lapse and auction — decided (Kaspaguy, 2026-09-29), one rule for every Plus name:**
  - After expiry + 30-day grace, anyone may call `reclaim`, which puts the name **up for auction**: it then has no owner, and its hold starts at that moment. Whoever holds the **auction key** at settlement time (held in the registry's state, rotatable by the root key) can settle it, so rotating the auction key never strands a held name. Free names never lapse. **[PROTO]**
  - **A held name has exactly two exits:** auction settlement, or release after 6 months (below). It can't be transferred, sold or renewed. **[PROTO]**
  - **Reserve price:** one month's subscription at the current monthly price. A bid below it doesn't settle; the name stays held and can be auctioned again. *(Note: the contract uses the price in force at settlement, not when the auction opened; the two can differ by at most one price change of ±50%. Storing the opening price would cost another leaf field.)* **[PROTO]**
  - **Holding is bounded:** if a held name isn't settled within **6 months** of the hold starting, anyone may `release` it. It then has no owner and no hold, and anyone can register it again through the doorman like a new name (`claimReleasedDirect` or `claimReleasedPrepaid`, the same payment as a new registration; the doorman signs a claim message of its own that includes the leaf nonce, so the name's original registration signature can't claim it back, SC-0023). A name nobody wants can't sit with the auction key forever. **[PROTO]**
  - **The winning bid includes the first 30 days of subscription;** the normal monthly price applies from day 31. At settlement that month's price is split like any subscription (75% of it to the treasury), and the rest of the bid goes to Kaspaguy. The winner can pay directly or with credits. **[PROTO]**
  - **Reserved names that were never registered** are auctioned the same way but settle through normal registration: once the winner has paid the bid, the doorman signs their registration (direct or credit path). The first month is split 25/75 on-chain as usual; the rest of the bid is paid to Kaspaguy before the doorman signs.
  - **No special rules for auctioned names.** After the first 30 days the winner renews like any Plus name; if they don't, the same 30-day grace applies, then the name lapses back to the auction key and is auctioned again.
- **Message credits expire every month (Kaspaguy, 2026-10-11, SC-0015).** Each paid Plus month comes with that month's message credits. They don't roll over: when the month renews, unused credits expire and the new month's credits replace them, and the treasury share of the expired month is swept out (§8.3). **Public wording:** "Unused credits are swept out every month at the time of replenishment."
  - **How the relay knows a credit's age without knowing the user:** blind tokens are issued under a key per day, and the relay accepts a token for 30 days from its key's day. The key says when a token was issued, not to whom. Trade-off, stated plainly: everyone whose month starts on the same day shares one key, so the anonymity set is the day's renewals; at launch that set is small.
  - **Top-up credits** (free tier) don't expire.
- **Published message guarantee.** The treasury's 75 KAS from each month pays network fees only:
  - at today's minimum fee (relay-paid through the spending pot: 0.005194 KAS since SC-0013, measured 2026-10-11; 0.006208 KAS measured with 2,048-byte payloads; 0.00527 KAS before SC-0012) that covers **about 14,400 relay-paid messages** (~12,000 at 0.006208 KAS);
  - even at the highest fee rate Kaspa has ever recorded (≈4,000 sompi/gram during the 2024 KRC-20 minting congestion, ≈0.21 KAS per 1,536-byte relay-paid message) it still covers **about 360 messages**.
  - *Correction (2026-09-29, approved by Kaspaguy):* the earlier "~24,000" used compute mass only (0.0031 KAS); the testnet measurement shows the size term binds.
  - **Published line (Kaspaguy, 2026-10-01):** "Your month includes up to ~12,000 one-to-one messages at today's Kaspa fees (fee measured 30 September 2026). A message to a full 4-person group costs 3 individual messages per send, so a month of only group messages covers up to ~4,000." Counting is per payload: a group send is one message per other member. Supersedes the 2026-09-29 line (~14,000 / ~4,700), which was based on the 0.00527 KAS fee before the spending pot (SC-0012). **Decided (Kaspaguy, 2026-10-11): the line is not a fixed number.** It is recomputed from the fee measured at the time of publishing and carries that date. At the 2026-10-11 measurement (0.005194 KAS, 1,536-byte payloads) it reads "up to ~14,000 one-to-one … up to ~4,800" (75 ÷ 0.005194 = 14,440; ÷ 3 = 4,813).
  - **"Up to" is load-bearing.** The monthly figure is what the month's 75 KAS covers at today's fee; the record-spike figure at a record fee spike is what the treasury can actually guarantee. Public wording must never imply the higher figure is guaranteed, and the reference indexer's treasury view (balance vs. recent spend) is reviewed regularly so a thinning treasury is seen early.
- **Screenshot protection — decided (Kaspaguy, 2026-09-29), Plus feature:** a Plus user can switch it on for a conversation; it's a setting carried inside the encryption, and every *official* app in that conversation honours it. **Honoured from any member (Kaspaguy, 2026-10-16, SC-0022):** apps offer the switch to Plus members only, but a receiver honours it whatever tier it sees for the sender, so a stale view of someone's tier can't leave a protected chat open. Downside, stated plainly: a modified app on a free account can switch it on too; the worst it does is keep the chat out of the web app. Someone whose Plus lapses can still switch their own protection off.
  - **Android:** screenshots and screen recording of the chat are blocked outright (the system's secure-window flag); the chat also goes blank in the recent-apps view.
  - **iPhone:** iOS gives apps no way to block screenshots. The app blanks the chat during screen recording and mirroring, uses the protected-layer technique that makes the chat come out blank in most screenshots, and **notifies the sender when a screenshot is detected**.
  - **Windows and Mac desktop apps:** the window is excluded from screen capture (Windows' capture-exclusion setting; macOS window sharing off).
  - **Web:** browsers can't block or detect screenshots, so a protected conversation **doesn't open in the web app**; the app says to use the phone or desktop app.
  - **Screenshot notices (built 2026-10-16, `WIRE_FORMAT.md` §7.2):** when a device detects a capture in a protected chat, its app posts a line in the chat on every member's device: "Screenshot detected: @name took a screenshot" (iPhone; Android 14 and later, where the system reports screenshot attempts even though the image comes out black), "Screen recording detected on @name's device" (iPhone), or "Possible screenshot detected on @name's device" (desktop, where only the screenshot key can be seen). The detecting device shows its own line too. Each notice is one encrypted message, paid from the detecting member's credits.
  - **Stated plainly:** it stops casual screenshots in official apps. It can't stop a photo taken with another phone, a rooted or jailbroken device, or a modified app. Marketed as "screenshot protection", never "screenshot-proof".
- **Encrypted cloud archive:** Plus users' history (sent and received) and their device sync are stored on Kaspaguy servers, **encrypted with the user's own keys**. Kaspaguy stores ciphertext it can't read. Storage and servers are paid from the dev share, since the treasury can only pay network fees.
- **Relay with blind tokens:**
  - Plus messages are broadcast by the Kaspaguy relay, which pays the fee from the treasury's spending pot (§8.3), so no user address appears on-chain.
  - Credits are issued as **blind tokens** (Privacy Pass style, RFC 9474 blind RSA or RFC 9497 VOPRF): the relay can check that a token is valid and unspent but can't link it to the payment that bought it.
  - Plus users can always fall back to sending with their own wallet if the relay is down.
- **Resale market:** names are resaleable, with **7.5% from each side to Kaspaguy** (standard brokerage): **the buyer pays price × 1.075; the seller receives price × 0.925; Kaspaguy receives the difference (price × 0.15).** The sale is atomic and authorised by the seller's owner key, which signs the buyer's key, the price and the payout address. **[PROTO]**
  - *Privacy note:* the buyer's funding wallet appears in the sale transaction next to the name, like a direct registration. Buyers who care use a fresh wallet; auction wins can be settled by Kaspaguy on the buyer's behalf through the credit path.
  - **Said plainly:** names may trade above the subscription price, and Kaspaguy earns a brokerage fee on that market like any marketplace. There is **no promise of value, no yield, no revenue share and no buyback**. A name still costs its monthly subscription to keep, and lapses without it.
- **Auctions:** Kaspaguy runs name auctions (reserved names, lapsed names). Bidding happens off-chain; the winner settles on-chain (`settleAuction`, or `settleAuctionPrepaid` with credits). The bid includes the first month: 75% of that month's price goes to the treasury, the rest of the bid to Kaspaguy.

### 8.3 The treasury: a black box with no withdrawals
Two covenants with **no withdrawal path at all**. Nobody, including Kaspaguy, can move treasury funds anywhere except into Kaspa network fees for Kaspaveil messages.

**The throttle replaces the monthly signing, not the relay key (decided, Kaspaguy, 2026-09-30).**
- **The relay key still does admission control.** Only messages it signs, from users who paid, are paid for.
- **The root key now replaces the relay key only when needed.** Its job shrank from "certify the relay key every 30 days" to "replace the relay key when it's lost or stolen".
- **How often, not whether.** The throttle changes how often the root is needed (never, in normal operation), not whether it's needed.

This replaces the first design (a daily drip into a hot wallet whose relay key needed a root certificate every 30 days; retired, SPEC_CHANGELOG SC-0012; the old contracts are in git history at 87da5e7, `contracts/retired/`).

- **Reservoir** (`contracts/reservoir.sil`) receives the 75% and has **no keys**. Its exits are `topUp()` and, for unused funds, `sweep()`; anyone may call either.
  - **Three reservoirs, one code (SC-0015):** each is compiled with the pot's covenant ID, a sweep age and the fixed Kaspaguy sweep address. One-month payments (and an auction win's first month) go to the **one-month reservoir, sweep age 30 days** (the credits expire when the month renews); 2–12 month prepayments go to the **prepayment reservoir, 360 days** (12 months; each month's credits still expire monthly, the money is swept when the longest prepayment has run out); top-up money will go to a **never-sweep reservoir** (sweep age 0) when the payment covenant is written, because top-up credits don't expire.
  - **Sweep:** once a reservoir UTXO is at least its sweep age old, anyone may move it, whole (at most 0.01 KAS fee), to the fixed Kaspaguy address, and nowhere else. The age is the input's relative DAA lock, enforced by consensus. No key is involved, so nobody can sweep early or redirect it. **[PROTO]** engine tests; testnet-10 2026-10-11 (below).
  - **Partial top-ups restart the clock:** the change of a partial top-up returns to the same reservoir as a new UTXO, so its age starts again. Top-ups draw the **newest** reservoir UTXO first, so money that has outlived its credits is left to be swept, and a restarted clock only ever touches money that was new anyway. By the time a deposit can be swept, every credit it paid for has expired.
  - A top-up is a two-input transaction (the pot, one reservoir UTXO).
  - It can move funds only into the genuine spending pot, recognised by the pot's covenant ID, or back into the reservoir, with at most 0.01 KAS for the network fee.
  - How much the pot may take is enforced by the pot (below). **[PROTO]**
- **Spending pot** (`contracts/treasury_hot.sil`): one covenant (one covenant ID) holding a small working balance. Its state:
  - the relay key;
  - the current 1-hour interval;
  - the fees paid in that interval;
  - a smoothed moving average (SMMA) of fees per interval;
  - a key nonce.

  Each relay-paid message must:
  - be a Kaspaveil message (Kaspaveil lane, payload 1–8 KB, one input, one output);
  - be signed by the relay key;
  - pay a fee of at most 1 KAS;
  - **keep the interval's total within the allowance.**

  The continuation must carry the pot's covenant binding and exactly the new state. **[PROTO]**
  - **Throttle — decided (Kaspaguy, 2026-09-30).**
    - **The rule (SC-0014, Kaspaguy 2026-10-10; 20 KAS floor confirmed 2026-10-11):** 1-hour intervals (36,000 DAA). The allowance is **max(20 KAS, 5 × SMMA)** per hour, where the SMMA runs over **N = 168 intervals** (one week). (4-hour intervals and N = 42 before 2026-10-11.)
    - **Updating the average:** at a new interval, SMMA ← (167 × SMMA + last interval's fees) / 168. Then, for each empty interval in between, a linear decay of 1/168 (zero after 168 empty intervals). That is a little faster than 168 more SMMA steps with zero fees, so after a quiet spell the allowance returns to the floor slightly sooner.
    - **Who applies it:** the first transaction in a new interval (a message or a top-up) applies the update and resets the counter.
  - **Why 5 × a smoothed average:**
    - A real burst of up to 5× normal use goes through at once.
    - A thief with the relay key can raise the limit only slowly. Spending everything allowed every interval moves the SMMA by at most ×(1 + 4/168) per interval, about **1.76× a day** (engine test: allowance 40 → 123 KAS over two days). At the floor a thief can burn up to 20 KAS an hour, 480 KAS a day, until the relay key is replaced.
    - Engine test, from 8 KAS per interval of normal use: the allowance went 40 → 119 KAS over two days. Day one's theft (304 KAS) was about 6 normal days of spending.
    - Unsmoothed, "5× the last interval" would have allowed ≈15,000× a day.
    - A regression was rejected: it needs a stored history in every message (about 13% more fee), and it projects a thief's steady ramp forward.
  - **The floor, 20 KAS per interval**, is a constant, fixed forever once published:
    - it keeps the pot usable at launch and after quiet spells;
    - it is also the most a thief can burn per interval while the average is low (120 KAS a day);
    - at 0.005194 KAS per message it is about 3,850 relay messages per hour.
    - **The value is proposed from the testnet-10 measurements and awaits the owner's confirmation before publication.**
  - **Top-ups keep the pot small.** A top-up is allowed only when the pot holds at most half of the interval's allowance, and it may never take the pot above the allowance. It must either fill the pot exactly to the allowance, or use the reservoir UTXO up and add at least 1 KAS, so nobody can dribble funds in to burn reservoir fees or tie up the pot cheaply.
  - **Time comes from the lock time.** The interval is the transaction's lock time ÷ 36,000.
    - The lock time must be a DAA score (below Kaspa's 500,000,000,000 timestamp threshold).
    - A lock-time check makes consensus enforce it: the check fails if the input's sequence would switch lock time off.
    - So nobody can move the pot into a future interval. A timestamp lock time, read as a DAA score, would have jumped the pot far into the future and frozen it, which is why it's refused.
  - **Replacing the relay key (root key):**
    - `replaceRelay` accepts a root signature over BLAKE2b-256("kasveil/v1/relay-replace" ‖ pot covenant ID ‖ new relay key ‖ nonce as 8 LE bytes). The covenant ID keeps a signature for one pot from being used on another; the nonce makes each signature single-use.
    - It changes nothing but the key and the nonce, and may take at most 0.01 KAS for its fee.
    - It works even when the interval's allowance is used up.
  - **Genesis and deployment order:**
    1. The pot is created in a transaction whose output 0 carries a new covenant ID, derived by consensus from the funding outpoint and that output. Nobody can mint another UTXO with that ID.
    2. The reservoir is compiled with that ID.
    3. The registry and the payment covenant are compiled with the reservoir's address.
  - **Engine tests** (real rusty-kaspa engine, real Schnorr signatures and covenant contexts; `contracts/tests/treasury_engine_tests.rs`, 8 tests) pass the valid cases and reject:
    - over the fee cap; any other destination; a continuation without the covenant binding; an extra output; the wrong lane; payloads under 1 KB or over 8 KB; a signature from a key that isn't the relay key;
    - a continuation that doesn't count the fee, inflates the SMMA or swaps the relay key; the interval moving backwards; a timestamp lock time; a final input sequence; two pot inputs; 1 sompi over the allowance;
    - top-ups when the pot is more than half full, above the allowance, dribbling, adding under 1 KAS, sending the change elsewhere, over the fee cap, taking from the pot, feeding a copy of the pot with another covenant ID, or changing the counters;
    - a replayed, non-root or other-pot replacement signature; a replacement that takes over 0.01 KAS, resets the throttle or pays out elsewhere; the reservoir spent on its own.
    - Plus a two-day thief simulation (every spend on the engine) and a 5× burst.
  - **Proven on testnet-10 (2026-09-30)**, with a pot whose root is the 2-of-3 FROST key of a simulated ceremony (`c7ad88c6…492d`):
    - **Setup:** genesis `8c478c3f…9dcc` (covenant ID `f95d664d…fc7e`); reservoir deposits of 75 and 15 KAS; a top-up that filled the pot to its 20 KAS allowance with change back to the reservoir (`edbf03f6…371f`).
    - **Relay-paid messages:** read back byte-identical (`cce36e4c…7399`, `39b6514f…49e5d0`). Minimum fee pinned at 620,800 sompi (620,799 rejected).
    - **Throughput:** 100 chained messages were accepted into the mempool in 10.3 s and all confirmed within 22.4 s. A single pot handles at least ~4.5 messages per second (≈16,000 per 1-hour interval) with a simple client.
    - **The allowance, on-chain:** the interval spent to within 0.29 KAS of 20 KAS. After a top-up the pot held 19.7 KAS, yet a 1 KAS message and a minimum-fee message beyond the allowance were both rejected. Exactly the remaining allowance was accepted.
    - **Attacks rejected by the node:** withdrawal, wrong lane, unbound continuation, uncounted fee, wrong key, timestamp lock time, final sequence.
    - **Relay-key replacement:** signed by two of the three simulated holders with the ceremony tool and accepted (`e29a4814…7432`). A replay of the same signature and a replacement signed by a non-root key were rejected.
    - **The next interval:** the replaced relay key was rejected, and the new one paid. That first message of the interval rolled the SMMA on-chain to 47,619,047 sompi, exactly (41 × 0 + 20 KAS) / 42, and reset the counter (block `8cc74381…5368`).
- **The root key** is the one key that matters. **Decided (Kaspaguy, 2026-09-29): a 2-of-3 threshold key (FROST)** on three physically separate devices held by three different people.
  - It produces an ordinary Schnorr signature, so the contracts see one key while signing needs two of the three.
  - The contracts can't enforce how the key is held, so this is an operating commitment, rehearsed on testnet before mainnet (§10 item 6).
  - It replaces the relay key (here) and the registrar, price and auction keys (registry, §8.5). **None of this is routine; in normal operation the root is never used.**
  - If two shares are lost, the root is gone: relay sending continues for as long as the relay key is safe, but a lost or stolen relay key (or registry key) could never be replaced.
- **No honeypot.** A stolen relay key can't withdraw anything. The most it can do is burn fees to miners at the throttled rate until the root replaces the key.
- **One pot at launch; split pots are a v2 option (Kaspaguy, 2026-09-30).** A single pot serialises relay messages. Several pots, each with its own throttle and floor, would parallelise them, at the cost of adding up the floors. Take it up once consumption reaches **70%**: sustained use at or above 70% of the allowance, or of the single pot's measured throughput.
- **Cover traffic** sent by the relay is paid from the pot like any message, so it counts towards the average; that keeps the allowance meaningful in quiet hours.
- **Consequence to know (SC-0015):** treasury funds can leave in two ways only: into the spending pot as message fees, or, once they have outlived the credits they paid for, whole to the fixed Kaspaguy address. Nobody can take them any other way, and nobody can take them early.
- **Sweep on testnet-10 (2026-10-11, reservoir compiled with a 600 DAA sweep age):** a 3 KAS deposit at DAA 593,995,826; a sweep submitted at once was **rejected by consensus** ("one of the transaction sequence locks conditions was not met"); the same transaction after the age was **accepted** at DAA 593,996,462 and paid 2.9991 KAS to the sweep address (`dd57df41…22fa`). A top-up from the new reservoir was accepted (`44d44124…6c3c`).

A rights holder's remedy is the normal resale flow (`sell`) or a court order compelling the owner to sign a transfer; the protocol needs no new power.

### 8.5 Roles: the building and the bouncer
- **The building** is the registry, treasury and message protocol: fixed code, no admin key. Nobody can seize a name, change the 25/75 split, withdraw from the treasury, or read a message.
- **Kaspaguy is the bouncer outside.** A registrar key co-signs every registration and applies the reserved list and anti-spam checks. **[PROTO on both registration paths]** It also runs the relay, the archive and the auctions, and **calls `reclaim` at each name's grace end** (§3.3), which makes the soft renewal and sale cut-offs exact in practice and sends lapsed names to auction on time. `reclaim` is permissionless, so if the doorman is down anyone can do it, and the app's past-expiry warning covers the gap.
- **Key rotation (must be in the first published contracts):** the offline **root key** can replace operational keys and do nothing else (no names, no split, no treasury). **Relay key: done**, stored in the spending pot's state and replaced by a root-signed `replaceRelay` only when it is lost or stolen (§8.3; the 30-day certificates were retired in SC-0012). **[PROTO]** **Registrar and price keys: done**, stored in each shard's state and replaced by a root-signed `rotateKeys`, which can't change anything else. **[PROTO]**
- **Bouncer limits:** it can refuse to let a new name in; it can't take away a name already inside, or touch anything in the building.
- **Auction settlements are on-chain and auditable.** Every `settleAuction` and `settleAuctionPrepaid` is a public transaction: the winning bid, the treasury's share (75% of one month's price) and the remainder to Kaspaguy are all visible. The contract refuses settlement below the reserve. The auction key signs the winner's key into the settlement, so a copied transaction can't redirect the name. **Stated plainly:** the auction key itself chooses the winner, so a stolen auction key could settle held names to its thief, but only by paying at least the reserve, with the treasury's share enforced; rotating the key (root) stops it.
- **The doorman is the arbiter** of who gets a new name: it gives names out first-come, and once it has signed for a name it holds that name for the requester for a few minutes and won't sign it for anyone else. Its signature binds the name to the requester's key, so once signed, nobody (the doorman included) can redirect that registration to someone else; the doorman's only power is to refuse.
- **Liveness, stated plainly:** the bouncer is needed for **new registrations** and for **credit-paid renewals** (§8.5a). Messaging, direct renewals, transfers, sales and treasury top-ups never need its signature, so an outage or a lost key can't make an existing name lapse or stop anyone talking: direct renewals always work and the 30-day grace period (§8.2) covers any outage (full story in §8.5a). If the registrar key is lost or compromised, **new sign-ups pause** until the offline root key rotates it (a matter of hours). There is deliberately no bypass: a registration route without the bouncer would also bypass the reserved list.
- **The reserved list is bouncer policy, not contract code.** It lives off-chain and can be updated after launch. The covenant doesn't check it, so **the bouncer's honesty is what protects against impersonation.** A name already registered before being added to the list can't be taken back, so the app name must be chosen and reserved before launch.

### 8.5a Paying for names without linking a wallet — decided (Kaspaguy, 2026-09-29)
- **The leak it closes:** paying for a Plus name straight from a personal wallet would publicly and permanently tie that wallet's balance and history to the username.
- **Two payment paths, both in the registry covenant:**
  1. **Credit path (default).** All money enters through one **payment covenant** carrying the hard-coded 25/75 split, and buys blind credits held on the user's device. The user spends credits for Plus months; the bouncer checks the credits and co-signs the registration or renewal as *prepaid*; the Kaspaguy relay submits it. No user wallet ever appears next to a name.
  2. **Direct path (opt-in).** Anyone may still register or renew by paying 25% to Kaspaguy and 75% to the treasury reservoir in the same transaction, exactly as in the current prototype. **The app warns that this links the paying wallet to the name.** This path never needs the bouncer for renewals.
- **Trust shift, stated plainly:** on the credit path the registry trusts the bouncer's "prepaid" signature, so **the registrar key can issue Plus months without payment.** It still can't seize, delete or read anything, and the 25/75 split stays hard-coded for all KAS that enters. So "no admin key" now carries an asterisk: *the bouncer can give names away.*
  - **Resales and auctions too:** the credit path also covers resale purchases and auction settlements: the buyer pays with credits and Kaspaguy's relay settles the sale on-chain, so the buyer's wallet never appears next to the name. A sale paid directly from the buyer's wallet (the direct path) links that wallet to the name, and **the app warns before the buyer confirms**.
  - **Audit trail:** the registry keeps a public, on-chain counter of prepaid registrations and prepaid months. Anyone can compare it with the money that entered the payment covenant, so comped names can't be hidden. **Audited by default:** both numbers are on-chain, so **anyone can compute and publish the comparison** with no permission and no trust in Kaspaguy.
  - **The same is true of every Kaspaguy-run role.** The reference indexer publishes, on one public page and API, the three on-chain views that bound Kaspaguy's discretion: (1) prepaid months issued vs. KAS received by the payment covenant; (2) the full list of auction settlements, with each winning bid, the treasury's share and the remainder to Kaspaguy, plus every reclaim and release; (3) the registry state itself, with its Merkle proofs. All three are computable from the chain by anyone, with no permission and no trust in Kaspaguy. The reference app shows the same three in its About screen.
- **Liveness, reconciled:**
  - New registrations always need the bouncer (it applies the reserved list).
  - Credit renewals need the bouncer, because it verifies the blind credits.
  - **Direct renewals never need it**, and the 30-day grace period covers bouncer outages. **A bouncer outage can never make a name lapse.**

### 8.6 Later / optional

## 9. Economics summary
| Stream | How | Where it goes | Enforced by |
|---|---|---|---|
| Plus subscription (~100 KAS/month) | 25 / 75 split | 25% Kaspaguy, 75% treasury (fees only) | registry covenant |
| Name resale | 7.5% from buyer + 7.5% from seller | Kaspaguy | registry sale entry |
| Auctions (reserved and lapsed names) | winning bid, including the first 30 days | 75% of one month's price to the treasury, the rest to Kaspaguy | registry `settleAuction` |
| Donations | kaspaguy.com board | Kaspaguy | — |

Real cost behind it: ~0.0052 KAS network fee per relay-paid message (0.005194 KAS for 1,536-byte payloads since SC-0013, measured on testnet-10 2026-10-11; 0.006208 KAS measured on testnet-10 with 2,048-byte payloads; paid by the treasury; 0.004628 KAS measured for a self-paid message), plus servers and storage (paid by Kaspaguy).

**Correction to a common belief:** Kaspa itself isn't quantum-safe. Its signatures (Schnorr and ECDSA on secp256k1) could be broken by a large future quantum computer, which would put *funds* at risk. **Kaspaveil messages are protected regardless**: their encryption uses hybrid post-quantum key exchange (ML-KEM-768 plus X25519), so recorded ciphertext stays unreadable even then.
